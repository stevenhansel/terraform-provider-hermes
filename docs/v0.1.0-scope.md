# v0.1.0 provider scope

Status: implementation contract

This document freezes the intended Terraform/OpenTofu surface for the first
supported release. The implementation is delivered in milestones, but all of
the domains listed here remain part of `v0.1.0`; milestones are not separate
release versions.

The provider manages durable Hermes dashboard state. It does not install the
Hermes container, create Kubernetes objects, configure an OIDC identity
provider, or provision secrets. Those concerns remain owned by the deployment
tooling and secret manager of the environment running Hermes.

## Contract evidence

Hermes does not currently publish a versioned management OpenAPI contract.
The dashboard documentation and the routers/models in the pinned Hermes image
are therefore the compatibility contract for this provider. Every resource
must have a sanitized response fixture and an acceptance test against the
exact pinned Hermes image before it is considered complete.

The relevant upstream references are:

- [Dashboard API documentation](https://hermes-agent.nousresearch.com/docs/user-guide/features/web-dashboard)
- [Model routes](https://github.com/NousResearch/hermes-agent/blob/main/hermes_cli/web_routers/models.py)
- [Profile routes](https://github.com/NousResearch/hermes-agent/blob/main/hermes_cli/web_routers/profiles.py)
- [MCP routes](https://github.com/NousResearch/hermes-agent/blob/main/hermes_cli/web_routers/mcp.py)
- [Messaging routes](https://github.com/NousResearch/hermes-agent/blob/main/hermes_cli/web_routers/messaging.py)
- [Cron routes](https://github.com/NousResearch/hermes-agent/blob/main/hermes_cli/web_routers/cron.py)
- [Skill routes](https://github.com/NousResearch/hermes-agent/blob/main/hermes_cli/web_routers/skills.py)
- [Toolset routes](https://github.com/NousResearch/hermes-agent/blob/main/hermes_cli/web_routers/tools.py)
- [Dashboard/plugin routes](https://github.com/NousResearch/hermes-agent/blob/main/hermes_cli/web_routers/dashboard_ui.py)

If a route or request shape changes, the provider must fail with a diagnostic
that identifies the unsupported capability. It must not silently fall back to
writing an entire `config.yaml` document.

## Resource surface

The table distinguishes remote CRUD from Terraform lifecycle behavior. A
Terraform resource may still be useful when Hermes exposes a setting rather
than a deletable object, but its destroy semantics must be visible in the
documentation and tests.

| Terraform type | Hermes surface | Remote lifecycle | v0.1.0 contract |
| --- | --- | --- | --- |
| `hermes_model_assignment` | `/api/config`, `/api/model/set` | Set/read; no safe delete | Included; destroy relinquishes state only |
| `hermes_custom_provider` | `/api/providers/custom-endpoints` | Upsert/read/delete; credential reference is external | Included for named non-secret endpoint metadata; raw API keys remain outside state |
| `hermes_profile` | `/api/profiles` | Create/read/update/delete; default is protected | Included for named profiles |
| `hermes_mcp_server` | `/api/mcp/servers` | Create/read/delete; enabled toggle; whole-map update exists upstream | Included for HTTP/SSE; `none`, header bearer provisioning via `bearer_token_env`, and interactive OAuth; config changes replace the registration and never use singleton whole-map replacement |
| `hermes_messaging_platform` | `/api/messaging/platforms/{id}` | Fixed catalog update/test; no create/delete | Included; destroy disables or clears managed settings |
| `hermes_cron_job` | `/api/cron/jobs` | Create/read/update/delete | Included |
| `hermes_skill` | `/api/skills`, skill toggle routes | Enable/disable existing skill | Included for activation state |
| `hermes_skill_installation` | skill hub install/uninstall/update | Background action | Included only with action-status polling and explicit ownership |
| `hermes_toolset` | toolset list/toggle routes | Enable/disable built-in toolset | Included for toggle state; no fake create/delete |
| `hermes_plugin` | `/api/dashboard/plugins/hub`, `/api/dashboard/agent-plugins/*` | Install/enable/update/delete for agent plugins | Included for verified agent-plugin routes; install is an explicit code-execution boundary |
| `hermes_dashboard_plugin` | filesystem-discovered dashboard plugins | No generic remote CRUD | Discovery data source or explicit action only; never arbitrary code execution |

The plugin entry has a compatibility gate because Hermes distinguishes agent
plugins from dashboard plugins. `hermes_plugin` manages only the verified
agent-plugin routes. Dashboard plugin discovery is filesystem-backed and is
not implemented as generic Terraform CRUD or arbitrary code execution.

Third-party application integrations are not provider-specific resource
types. They will normally be represented by `hermes_mcp_server`
registrations, with the actual MCP adapters deployed and owned by the
surrounding deployment tooling. The provider must not invent
MCP URLs or credentials for an application that has no verified adapter.

## Resource conventions

### Profile scoping

Every profile-scoped resource has a `profile` attribute and includes the
profile in its canonical ID. New resources require an explicit profile. The
existing model assignment keeps its optional profile for compatibility with
the already-adopted state and examples; new configurations should set it
explicitly.

Profiles are namespaces, not authorization boundaries. One authenticated
dashboard session can access every profile on the Hermes instance. Acceptance
tests therefore use both a disposable profile and a disposable Hermes
instance when testing destructive or security-sensitive behavior.

### State and identity

Resource IDs are remote identities, not display names. IDs must be stable
under refresh and import. Each resource implements:

1. canonical ID construction;
2. strict import parsing;
3. missing-object handling by removing the object from state;
4. canonicalization of server defaults;
5. preservation of write-only values when Hermes omits them from reads.

List and map values must not be modeled as unordered JSON strings. Use typed
framework attributes and deterministic sorting/canonicalization so harmless
server ordering does not create perpetual plans.

### Mutations and concurrency

The client serializes mutations per Hermes endpoint. Hermes exposes a whole-map
MCP `PUT`, but the first singleton resource implementation uses the safer
create/delete and enabled-toggle routes for its supported lifecycle. It marks
transport/config changes as replacement-required and never replaces the map
with a single resource's entry. A future in-place MCP update must read the
complete map, modify only its owned entry, and write it while holding the
lock.

Operational actions such as MCP testing, cron triggering, skill installation,
and plugin updates are explicit resources or provider methods. They are not
silently executed during `Read`, refresh, or an unrelated attribute update.

### Secrets

The provider supports a machine-only Hermes basic dashboard login. An OIDC
dashboard provider can remain the human dashboard login and is not automated through browser
PKCE. Provider credentials come from `HERMES_DASHBOARD_USERNAME` and
`HERMES_DASHBOARD_PASSWORD` or an equivalent secret injection mechanism.

Sensitive values require a separate state decision; `Sensitive` only hides a
value from normal CLI output and does not remove it from state. The preferred
v0.1 pattern is:

- keep API keys, bot tokens, OAuth secrets, and MCP environment values in an
  external secret manager;
- pass an environment-variable name or Hermes-supported reference to the
  provider where Hermes supports it. The MCP bearer path resolves the named
  variable only during create and retains only the variable name;
- reject raw secret attributes where the Hermes API cannot read them back
  safely, unless a documented state tradeoff is explicitly accepted;
- redact request/response logging, errors, traces, and fixtures.

No acceptance test may use a real messaging token, OAuth credential, or
production application secret.

## Milestone and commit plan

Each milestone should be a small, independently reviewable conventional
commit or commit series. A later milestone may not hide a broken earlier
contract behind a large refactor.

### 0. Freeze the contract

Create sanitized fixtures from the pinned Hermes image, record endpoint and
version assumptions, define import IDs, and document ownership and secret
policy. Gate: schema review and fixture decoding tests.

Suggested commit: `docs(scope): define v0.1.0 provider surface`.

### 1. Establish package boundaries

Move the typed dashboard transport into `internal/hermes`, keep Terraform
framework resources in `internal/provider/<domain>`, and put reusable test
servers/fixtures in `internal/testutil`. Preserve the current model resource
behavior while moving it. Gate: `go test`, `go test -race`, `go vet`, lint,
and a no-diff generated documentation check.

Suggested commits:

- `refactor(client): introduce Hermes API package boundary`
- `refactor(provider): split model assignment domain`

### 2. Complete model and provider foundations

Add common profile query handling, typed errors, capability checks, model
options/status data sources, and the custom-provider resource only after its
write contract is pinned. Gate: import, drift, unknown/null, and missing-value
tests.

Suggested commits:

- `feat(client): add shared profile and error semantics`
- `feat(provider): manage custom providers and model discovery`

### 3. Add profiles and MCP

Implement named profile CRUD with protection for the default profile. Add MCP
HTTP/SSE registrations first. Treat immutable transport/config fields as
replacement-required, preserve unmanaged servers during whole-map writes, and
keep stdio execution behind an explicit security gate.

Suggested commits:

- `feat(api): add profile and MCP clients`
- `feat(provider): manage profiles and MCP servers`

### 4. Add messaging configuration

Model messaging as a fixed platform catalog with `for_each`-friendly
configuration. The resource updates and tests an existing platform; it does
not claim to create a new transport. Implement disable/clear behavior only
where the pinned Hermes version proves that it is safe. Keep all tokens
external to state.

Suggested commits:

- `feat(api): add messaging platform client`
- `feat(provider): manage messaging platform state`

### 5. Add cron, skills, toolsets, and verified plugins

Implement real cron CRUD first. Separate durable enablement from background
skill-hub installation. Add toolset toggles as toggles, not fake objects. Add
only plugin routes verified against the pinned Hermes image; dashboard plugin
filesystem discovery is not a generic install mechanism.

Suggested commits:

- `feat(api): add cron and extension clients`
- `feat(provider): manage cron jobs and extension state`

### 6. Release hardening

Validate the provider end to end with a composed configuration using maps and
`for_each`, and keep deployment/network/secret resources outside the
provider. Run unit, API-contract, acceptance, race, documentation, and
GoReleaser gates.

Suggested commits:

- `test(acceptance): cover v0.1.0 resource lifecycles`
- `docs(provider): finalize v0.1.0 documentation`
- `release: prepare v0.1.0`

## Quality gates

The release is not complete until all of the following pass:

- `gofmt` check, `go vet`, `go test ./...`, and `go test -race ./...`;
- client HTTP tests for cookies, 401/403 re-authentication, profile query
  propagation, bounded response bodies, redaction, and write locking;
- resource tests for schema validation, import, create/read/update/delete,
  drift, remote deletion, unknown values, and write-only secrets;
- contract fixtures for every supported Hermes endpoint and negative responses;
- acceptance tests against the pinned Hermes image, with no production profile
  or real messaging secret;
- generated Registry documentation and `tfplugindocs validate`;
- GoReleaser configuration, snapshot archives, checksums, and signing checks.

## Security release blockers

Before enabling broad tools or messaging in a deployment:

- keep human dashboard login (for example OIDC) separate from the basic
  account used for IaC;
- restrict network access to the dashboard to the intended ingress and
  Terraform/OpenTofu runner paths;
- treat profiles as namespaces only, never as tenant security boundaries;
- do not enable unreviewed stdio MCP commands or arbitrary plugin execution;
- do not allow deployment tooling (for example Helm) and Terraform/OpenTofu to
  own the same Hermes configuration field;
- document every destroy operation that disables, clears, or intentionally
  leaves remote state unchanged.
